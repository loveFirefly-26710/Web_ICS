# Web_ICS 立项设想

这份文件写于动手之前。它记的是当时对这件事的判断和打算：为什么要做、要做到什么程度、
打算怎么做、怕的是什么。

它不记录后来实际做成了什么。那些写在 [README](../README.md) 和
[DEVELOPMENT](../DEVELOPMENT.md) 里。想对照「当初打算的」和「最后做出来的」差在哪，
看那两份。

## 背景

### 手上这批文档

要读的是华为的产品文档包，`.hdx` 与 `.hwics` 两种扩展名，一共 59 个，合计 11.5 GiB。
单文件从 1.7 MB 到 600 MB 不等。

打开看过之后发现，这些包本质上是标准 ZIP，内部就是普通的静态 HTML 加图片，
正文里的资源引用全是相对路径。这件事决定了整个方案能有多简单：不需要实现任何私有
解包逻辑，也不需要改写 HTML。

### 官方阅读器为什么用不了

官方阅读器是 ICS Lite。它的技术栈是 Java 加 Spring MVC 加内嵌 Tomcat 加 Derby
加 Aspose，190 个 jar、266 MB，自带 JRE。索引与预览进程按 `-Xms128m -Xmx1024m`
配置，导出进程给到 `-Xmx4096m`。

问题不在于它做得不好，而在于它要跑的地方没有这个资源。目标是一台 2 核、1 GB 内存的
服务器，光常驻 JVM 就把上限吃满了，还得和系统、和其他服务分。

它真正有价值的部分是「管理加检索加阅读界面」这三件事，不是解密（包根本没加密），
也不是 Office 预览（这批文档里 Office 附件几乎没有）。所以打算只把这三件事重写一遍。

### 目标场景

一台 2 核 1 GB 的小服务器，通过 Docker 或一个二进制跑起来，用浏览器访问。
偶尔可能有几个人同时看，不会更多。文档库只读，挂在宿主机上，不进镜像。

## 目标与硬约束

| 项 | 要求 |
|---|---|
| 硬约束 | 阅读器进程 RSS 不超过 1 GB，设计目标 400 MB 以内 |
| 目标平台 | Linux Docker 为主，Windows 也要能跑 |
| 数据源 | 59 个文档包（`.hdx` / `.hwics`），11.5 GiB，只读 |
| 功能边界 | 只做「能读、能搜、能跑在 1 GB 里」，其余一律不做 |
| 交付形态 | 单二进制（`CGO_ENABLED=0`）加 Docker 镜像 |
| 对照基准 | 官方 ICS Lite 在同负载下占用 756 MB，这是要打败的靶子 |

目标为什么定 400 MB 而不是贴着 1 GB：Go 的 GC 在受限环境里会先把 RSS 撑高再回收，
如果目标就贴着上限，实际运行必然越界。必须有意把目标压到远低于上限，
留出抖动空间。

另外，1 GB 是这台机器的一半，另一半要留给系统和别的服务。400 MB 这个数字不是
从「最多能用多少」倒推的，是从「至少要留多少给旁边」正推的。

## 动手前的调研

写代码之前先把两个对象拆开看了：文档包本身，和官方阅读器。有几条结论直接决定了
架构，这里按当时量到的原始数据记下来。

### 文档库实况

| 项 | 结果 |
|---|---|
| 文件数 | 59（53 个 `.hdx` 加 6 个 `.hwics`） |
| 总体积 | 11.5 GiB（单文件 1.7 MB 到 600 MB） |
| 文件类型 | 全部是标准 ZIP（magic `PK\x03\x04`），不是私有加密格式 |
| 内部结构 | `resources/` 下是普通静态 HTML 加 PNG/JPG/PDF，正文资源引用全是相对路径 |
| HTML 规模 | 828,636 个，未压缩 6.48 GiB；剥掉标记后的纯文本 1.61 GiB |
| 目录元数据 | 59/59 都有 `.hhc`，55/59 有 `resources/navi.xml`（结构化 XML，最干净），其余用 `FileList.xml` 加 `.hhc` |
| 全文索引 | 部分包内置 Lucene 索引，部分没有，不可依赖 |
| Office 附件 | 极少，多数包为 0 |

### 由此得到的三个简化

1. 不需要任何私有解包逻辑。HDX 与 HWICS 就是 ZIP，标准库 `archive/zip` 直接读。
2. 阅读本质上是「静态文件服务器加一个浏览器外壳」。正文 HTML 的自引用全是相对路径，
   按原始目录层级直出即可，不需要改写 HTML。
3. 目录树可以直接从包里读，不需要自建一份索引库。

### 官方阅读器的成本基线

这部分是从发行包里反汇编得到的，用 `javap -p -c -v` 读 class，读 `searchcommon.js`
还原合并算法。反汇编出来的才是事实。

- 检索用 Apache Lucene 8.11.2，索引字段 `t_title`（权重 10）、`t_content`（权重 1）、
  `tp_keywords`。组合方式是 `BooleanQuery` 加 `BoostQuery` 加 `Occur.SHOULD`，
  也就是并集。界面只有一个输入框，没有「标题还是正文」的二选一。
- 分页首屏 100 条、后续 15 条。
- 标题命中的合并键是 `title`，且只合并第 1 页。

顺带纠正一个直觉上的错误：原版并不是「标题一个 tab、正文一个 tab」。
它是一次查询同时打两个字段，靠权重差排序。这条如果猜错了，整个检索设计都会跟着错。

### 内存预算

动手前定的预算表：

| 项 | 预算 |
|---|---|
| Go 运行时加框架 | 25 MB |
| 当前展开的目录树（LRU，最多 1 个包） | 50 MB 以内 |
| zip 中央目录缓存（59 个包） | 20 MB 以内 |
| HTTP 连接与请求缓冲 | 30 MB 以内 |
| 大 PDF 流式中转（峰值） | 16 MB 以内 |
| 运行时余量（GC 抖动、临时分配） | 100 MB 以内 |
| 进程稳态合计 | 约 240 MB |
| 硬上限（含峰值） | 400 MB 以内 |

这张表里没有「全文索引」这一项，因为当时把全文检索列为不做（见下面的
[明确不做的](#明确不做的)）。如果后面要做，预算得重算。

### 磁盘预算

文档库本身 11.5 GiB 只读挂载，不占额外空间。唯一打算新增的磁盘占用是正文语料库：
按 1.61 GiB 纯文本加索引开销估算，落在 1.8 GiB 以内。这份语料随时可以重建，
所以不视为长期负担。

## 预期范围

### 要做成的三件事

1. 「能读」。首页列出全部文档包，点进去是目录树加正文 iframe，正文里的图片、脚本、
   PDF 都能正常加载，目录树能逐层展开、能定位到某一篇。
2. 「能搜」。一个输入框，一次查询同时覆盖标题与正文，结果带摘要与所在章节路径，
   能翻页，且任何一页报出的总数都是精确的。
3. 「能跑在 1 GB 里」。稳态内存压在 400 MB 以内，压力上来时先降级而不是被容器杀掉。

这三件事之外的一切，默认不做。

### 明确不做的

- 倒排索引与中文分词。原版用 Lucene，这里打算换成磁盘语料库加全库顺序扫
  （见[预算与依据](#磁盘预算)）。
- 批注与笔记（原版的 `docnote`）。
- Office 在线预览与导出。这是原版最大的重依赖，而这批文档里 Office 附件几乎为 0。
- 打印导出、版本对比、下载任务管理、虚拟文件夹。
- 用户体系（用户名密码、角色、按人授权）与隐私声明。
- 任何写操作。服务是只读的。

### 对照基准：要做到什么程度

| 维度 | 官方 ICS Lite | 打算做到 |
|---|---|---|
| 技术栈 | Java 加 Spring 加内嵌 Tomcat 加 Derby 加 Aspose，190 个 jar / 266 MB | Go 单二进制，依赖控制在一个 |
| 同负载内存 | 756 MB（141 加 616 两个进程） | 400 MB 以内，目标稳态 240 MB |
| 检索 | Lucene 全库正文倒排索引，索引规模 1 到 3 GB | 标题常驻列式索引加正文磁盘语料库全扫 |
| 检索入口 | 一个输入框加一个「范围」下拉 | 一个输入框，范围由页面上下文决定 |
| 标题与正文权重 | `t_title` 10 与 `t_content` 1，并集 | 同一语义，用整数分级表达 |
| 主题合并 | 按 `title` 合并，仅第 1 页 | 按 `(title, url)` 合并，覆盖所有页 |
| 资源查找 | 大小写不敏感 | 必须一致，否则这批文档打不开 |
| 目录树 | zTree 异步懒加载 | 同样的懒加载思路，加单包 LRU |
| 接口数 | 232 个 | 按「不做多余处理」裁剪到个位数 |
| 交付 | 自带 JRE 的目录树 | 单二进制加 Docker 镜像 |

内存那一行是整件事的动机，其余各行都是它的推论：为了压到 400 MB，
能砍的依赖、能砍的索引、能砍的接口都要砍。

## 初步规划

### 阶段设想

按「每一步都能单独跑起来」切，而不是按模块切：

| 阶段 | 打算做什么 | 做完能验证什么 |
|---|---|---|
| S1 | Go 骨架、库列表接口、`/healthz` | 能列出 59 个包，进程能起能停 |
| S2 | 目录树懒加载（`navi.xml` 流式解析、`.hhc` 兜底、单包 LRU） | 大包的目录树能在 1 秒内展开，内存不涨 |
| S3 | 正文 iframe 流式直出与资源加载 | 正文里的图片、脚本、PDF 都正常 |
| S4 | 界面对齐原版布局，加上下篇与面包屑 | 能连续读，不用回首页找下一篇 |
| S5 | 内存守卫、并发闸门、Docker 与 Windows 打包 | 压测不掉线，两个平台都有产物 |
| S6 | 2 核 1 GB 压测与调优 | 稳态内存落在预算内 |

标题检索、全文检索、客户端证书这些都不在这六步里。它们是「如果前六步跑通了、
还有余力才做」的部分。

### 交付形态设想

- Linux：单个静态链接二进制（`CGO_ENABLED=0`），加一个 Alpine 基础镜像。
  镜像里只放可执行文件，不放前端目录，也不放文档库。
- Windows：只发一个自包含的 exe，拷到任意目录双击就能用。前端资源内嵌进去，
  所以不需要旁边的目录。不做安装包。安装包相比单文件只多一个开始菜单快捷方式，
  却要拉进整条安装器工具链，不划算。
- 文档库与语料库都不进镜像，运行期挂载。

### 部署形态设想

主形态是 Docker Compose：文档库只读挂载，语料库放一个可写卷，端口对外由反向代理管。
没有 Docker 的机器退回二进制加 systemd。

镜像在 CI 上构建、推到镜像仓库，服务器只负责拉取。目标机器是 2 核 1 GB，
在上面编译会把正在提供服务的进程拖垮。

## 预期风险与应对设想

按「发生概率」排，不按严重程度排。排在前面的都是几乎一定会碰上的。

| 预期风险 | 会发生什么 | 打算怎么应对 |
|---|---|---|
| 内存压不住 | Go 的 GC 按宿主机总内存决定回收时机，RSS 一路涨到被容器 OOM Kill | 显式设 `GOMEMLIMIT`，再加应用内的内存守卫：先清缓存，再降级拒绝新请求 |
| 中文编码 | 正文 HTML 声明 `charset=gb2312` 而字节是 GBK，按 UTF-8 解码全是乱码，中文永远搜不到 | 抽取文本前显式转码，不依赖声明 |
| 大小写不匹配 | 包内条目名统一小写，而正文与目录里的 URL 保留原始大小写，会有大面积图片与脚本 404 | 资源查找做大小写折叠回退，且必须是 O(1) 的索引，不能每次线性扫 |
| 前端资源缓存不一致 | 浏览器把旧版 CSS 与新版 JS 混着用，页面半新半旧 | HTML 外壳不缓存，静态资源走协商缓存，引用带版本号 |
| 目录树全量常驻 | 59 包目录全解析约需 867 MB，直接越过上限 | 缓存容量固定为 1，只留当前正在看的那一个包 |
| 全库正文检索装不下 | 倒排索引按规模估算要 3 到 9 GB，1 GB 预算里没有位置 | 先量数字再定方案。若纯文本扫描吞吐够，就不建索引，改成落一份磁盘语料库顺序扫 |
| 网页服务没有认证 | 一旦对外暴露等于把内部文档公开 | 默认只监听本机或交给反向代理；需要更强控制时在进程内做客户端证书认证，不引入必需的外部进程 |
| 并发扛不住 | 2 核机器上并发稍高就雪崩 | 全局在途请求上限，超出直接快速失败；检索类接口再加每 IP 限流 |
| 文档库只读挂载 | 语料库默认建在文档库下面，只读时写不进去 | 语料目录单独可配，文档库只读挂载时显式指到别处 |
| 语料与代码脱节 | 改了正文抽取逻辑，但旧语料「比包新」被当成有效，结果一直不变 | 给语料格式加一个抽取版本号，改抽取逻辑就必须加一，版本不符即重建 |
| 大文件拖慢整体 | 单个 PDF 可以很大，读它会占住并发槽位 | 大文件单独限流，全程流式中转，不落内存 |

## 附：本文数字的来源

本文的调研数字来自对 59 个文档包的实际扫描（ZIP 结构、元数据体量、目录节点数、
正文引用方式）、对官方发行包的架构剖析（反汇编 class 与 JS），以及本机实测。

这条要求打算一直沿用：能实测的就实测，不能实测的写清楚是拍定值，别让拍脑袋的数字
